## 논문을 보고 공부한 핵심 내용

## SyzDescribe의 전체 핵심

SyzDescribe는 커널 소스에서 단순히 <code>ioctl</code>이라는 이름이나 비슷하게 생긴 구조체를 찾는 방식이 아니다. 저자들은 <strong>Linux 커널 코어와 드라이버 사이에서 오랫동안 유지되어 온 초기화·등록 규칙과 프로그래밍 관례를 모델링</strong>하고, 그 규칙을 따라가면서 실제 드라이버 인터페이스를 정적으로 복구한다.

커널 모듈의 초기화 함수를 찾은 뒤, 드라이버 객체와 장치 객체를 식별하고 장치 번호를 이용해 서로 연결한다. 여기서 드라이버 객체에서는 시스템 콜 핸들러를, 장치 객체에서는 장치 파일 이름을 복구한다. 이후 <code>ioctl()</code> 핸들러 내부를 분석하여 명령 값과 인자 형식을 알아내고, <code>open()</code>으로 얻은 파일 디스크립터가 아닌 <strong>추가 파일 디스크립터 의존 관계</strong>도 복구한다.

최종적으로 얻은 정보를 syzkaller가 읽을 수 있는 <strong>syzlang 형식의 시스템 콜 설명</strong>으로 변환한다.

## 이 논문에서 가장 중요한 관점

<strong>겉모습이 시스템 콜 핸들러처럼 보이는 코드와 실제 사용자 공간의 시스템 콜을 처리하는 코드는 다를 수 있다.</strong> 따라서 특정 구조체 이름이나 주변 문자열만 보고 판단하지 않고, 커널 드라이버가 실제로 초기화되고 등록되는 전체 과정을 따라가야 정확한 인터페이스를 복구할 수 있다는 것이 저자들의 핵심 주장이다.

## 지식

syscall: 사용자 프로그램이 커널에 요청을 보낼 때 거치는 통로로, 사용자 프로그램이 원하는 기능에 맞는 syscall을 호출하면 커널이 해당 요청을 처리할 수 있도록 연결해준다.

파일 디스크립터(File Descriptor, FD) : 프로세스가 열어 놓은 파일이나 장치를 식별하기 위해 사용하는 정수형 번호

## 초록

운영체제 커널에 대한 퍼징은 실제 버그와 취약점을 찾는 데 효과적인 방법으로 사용되고 있으며, 대표적인 Linux 커널 퍼저인 <strong>syzkaller</strong>는 많은 버그를 발견해 왔다.

그러나 syzkaller가 커널 드라이버를 효과적으로 퍼징하려면 <strong>어떤 시스템 콜을 호출할 수 있는지, 어떤 값이 필요한지, 시스템 콜 사이에 어떤 의존 관계가 있는지</strong>를 알려주는 시스템 콜 설명이 필요하다.

기존 시스템 콜 설명은 대부분 사람이 직접 작성하기 때문에 작성과 유지보수에 시간이 많이 들고, 누락·오류·오래된 정보가 생길 수 있다. 특히 Linux 커널 드라이버는 계속 추가되고 변경되기 때문에 모든 드라이버의 설명을 사람이 지속적으로 관리하기 어렵다.

저자들은 이 문제를 해결하기 위해 <strong>SyzDescribe</strong>를 제안한다. 핵심은 Linux 커널 코어와 드라이버 사이의 계약에서 나타나는 <strong>불변적인 구조와 프로그래밍 관례를 모델링</strong>하는 것이다. 이를 이용하면 드라이버가 어떻게 초기화되고 사용자 공간에 어떤 인터페이스를 제공하는지 프로그램적으로 복구할 수 있다.

평가 결과, SyzDescribe가 생성한 시스템 콜 설명은 기존 자동화 연구인 <strong>DIFUZE와 KSG보다 전반적으로 더 정확했으며</strong>, 사람이 관리하는 syzkaller 설명과 비교해도 경쟁력 있는 결과를 보였다.

> 커널 드라이버가 따르는 오래된 초기화·등록 규칙을 정적 분석하여 syzkaller가 사용할 시스템 콜 설명을 자동으로 생성하는 연구이다.

## 1. 서론

syzkaller는 단순히 무작위 시스템 콜을 계속 호출하는 방식만으로 동작하지 않는다. 효과적인 퍼징을 위해서는 운영체제가 제공하는 시스템 콜, 각 호출에서 의미 있는 값, 호출 순서 사이의 명시적인 의존 관계를 알고 있어야 한다.

syzkaller에서는 이런 정보를 <strong>syzlang</strong>이라는 선언적 언어로 작성한다.

- <strong>syscall 설명:</strong> syzkaller에게 특정 시스템 콜을 어떤 방식으로 호출해야 하는지 알려주는 명세
- <strong>인자:</strong> 함수나 시스템 콜을 호출할 때 함께 전달하는 입력값
- <strong>의존 관계:</strong> 앞선 시스템 콜의 결과가 뒤의 시스템 콜을 실행하는 데 필요한 관계
- <strong>syzlang:</strong> 시스템 콜 설명을 syzkaller가 읽을 수 있게 표현하는 전용 언어

```c
KVM(Kernel-based Virtual Machine) = 리눅스에서 가상머신을 만들고 실행할 수 있게 해주는 커널 기능

```

<strong>기존 syscall 설명은 대부분 사람이 수동으로 작성한다.</strong> 이 때문에 인터페이스나 의존 관계가 빠질 수 있고, 잘못된 정보가 들어가거나 커널이 변경된 뒤에도 오래된 설명이 남을 수 있다. 논문은 불완전한 시스템 콜 설명이 syzkaller의 코드 커버리지를 제한하는 주요 원인 중 하나라고 설명한다.

또한 Linux 커널 코드에서 드라이버가 차지하는 비중이 매우 크기 때문에, 드라이버 설명이 부족하면 커널 공격 표면의 상당 부분을 충분히 퍼징하지 못할 수 있다.

```c
기존 자동화 연구

DIFUZE는 정적 분석을 사용하지만 드라이버 프로그래밍 관례를 충분히 모델링하지 않아 부정확한 결과가 생길 수 있다.
KSG는 동적 분석을 이용하지만 실제 시스템에서 드라이버가 이미 로드되어 있어야 하고, 재컴파일·계측된 커널 환경을 준비해야 한다는 제약이 있다.
```

> 따라서 저자들은 <strong>정확한 시스템 콜 설명을 자동으로 생성하는 문제는 아직 충분히 해결되지 않았다</strong>고 보고 SyzDescribe를 제안한다.

## 2. 배경 및 연구 동기

### 2.1 리눅스 커널 드라이버와 시스템 콜 설명

Linux의 드라이버는 일반적으로 커널 모듈 안에 존재한다. 커널 모듈은 부팅 과정에서 포함되어 실행될 수도 있고, 필요할 때 별도로 로드될 수도 있다.

커널 모듈에는 초기화 과정이 존재하며, 흔히 <code>module_init()</code> 같은 매크로를 통해 초기화 함수를 선언한다. 이 초기화 함수에서 드라이버가 사용할 자료구조와 사용자 공간에 노출할 인터페이스가 설정된다.

```c
사용자 프로그램은 장치 드라이버의 내부 함수를 직접 호출하지 않고,
open() = 파일이나 장치를 연다. 성공하면 그 대상을 가리키는 fd를 받음
read() = fd가 가리키는 대상에서 데이터를 읽는다.
write() = fd가 가리키는 대상에 데이터를 쓴다.
ioctl() = read/write만으로 표현하기 어려운 장치 전용 제어 명령을 보낸다.

위와 같은 시스템 콜 인터페이스를 사용한다.
```

장치 드라이버의 시스템 콜 설명을 작성하려면 대표적으로 다음 정보가 필요하다.

- 어떤 장치 파일을 열어야 하는가
- 어떤 시스템 콜 핸들러가 존재하는가
- <code>ioctl()</code>에서 어떤 명령 값을 사용할 수 있는가
- 명령마다 어떤 인자 형식이 필요한가
- 앞선 호출의 결과가 뒤 호출에 필요한 의존 관계가 존재하는가

### 2.2 시스템 콜 설명 자동 생성에 대한 기존 시도

#### 동적 분석 기반 방법

동적 분석은 실제 실행 중인 커널을 관찰하여 드라이버와 인터페이스를 복구한다.

<strong>KSG는 실제로 실행 중인 드라이버를 관찰해서 syscall description을 만드는 방식이지만, 실행되지 않은 드라이버나 하드웨어가 없는 드라이버는 분석하기 어렵다.</strong>

#### 정적 분석 기반 방법

DIFUZE는 Linux와 Android 커널 드라이버의 소스 코드를 정적 분석하여 시스템 콜 설명을 자동 생성하려고 시도했다.

<strong>DIFUZE는 미리 정해둔 구조체 타입이나 주변 문자열 같은 휴리스틱을 이용해 syscall handler와 장치 파일 이름을 추정하기 때문에, 실제가 아닌 것을 잘못 찾거나 실제 인터페이스를 놓칠 수 있다.</strong>

```c
휴리스틱(heuristic)
- 정확한 관계를 완전히 증명하는 대신,
  경험적인 규칙이나 특징을 이용해서 빠르게 추정하는 방법
```

#### 정적 분석과 동적 분석의 비교

동적 분석은 실행 중인 정보를 직접 확인할 수 있지만 실제로 실행되지 않은 드라이버를 보기 어렵다. 정적 분석은 실행 환경 없이 더 넓은 코드를 살펴볼 수 있지만, 단순한 패턴만 사용하면 정확도가 떨어질 수 있다.

SyzDescribe는 정적 분석을 선택하되 <strong>드라이버가 실제로 초기화되고 등록되는 구조를 모델링하여 정확성을 높이는 방향</strong>을 사용한다.

> 저자들은 기존 연구인 KSG가 실제 실행 상태를 기반으로 분석하기 때문에 <strong>실제로 로드되고 초기화된 드라이버에 분석 범위가 제한될 수 있다는 점</strong>을 지적한다. 반면 DIFUZE는 실행 환경 없이 정적 분석이 가능하지만, <strong>휴리스틱에 의존하기 때문에 정확도에 한계가 있을 수 있다</strong>고 본다.
>
> 이러한 기존 방식의 한계를 바탕으로 저자들은 <strong>실행 환경에 대한 의존성을 줄이면서도 기존 정적 분석보다 더 정확하게 시스템 콜 설명을 생성하는 방법</strong>을 제안하고자 했다. 이를 위해 SyzDescribe는 정적 분석을 사용하되, Linux 커널 드라이버가 실제로 초기화되고 등록되는 구조와 프로그래밍 관례를 모델링하여 분석 정확도를 높이는 방향을 선택했다.

## 3. SyzDescribe 설계

<strong>SyzDescribe는 Linux 커널 드라이버를 정적 분석해서 syzkaller가 사용할 시스템 콜 설명을 자동으로 만드는 도구이다.</strong>

핵심은 코드에서 <code>ioctl</code> 같은 이름만 찾는 것이 아니라, <strong>드라이버가 실제로 어떻게 초기화되고 장치와 핸들러가 어떻게 연결되는지 따라가는 것</strong>이다.

### 3.1 동기 부여 예시

이 절의 핵심은 <strong>겉으로 시스템 콜 핸들러처럼 보이는 코드와 실제 사용자 요청을 처리하는 핸들러는 다를 수 있다</strong>는 점이다.

SyzDescribe는 먼저 <code>module_init()</code> 같은 정보를 통해 드라이버 초기화 지점을 찾는다. 그 뒤 드라이버 객체와 장치 객체를 확인하고, <strong>major/minor 장치 번호</strong>를 이용해 두 객체가 같은 인터페이스에 속하는지 연결한다.

```c
커널 모듈(kernel module)
- 리눅스 커널에 필요할 때 추가로 붙였다 땔 수 있는 코드 조각

예시
- Linux 커널 전체에 모든 드라이버 기능을 처음부터 다 넣어두면 너무 커지고 관리도 힘들어진다.
  그래서 USB 드라이버, 네트워크 드라이버,
  특정 파일시스템 같은 기능을 모듈 형태로 따로 만들어 두고 필요할 때 커널에 로드할 수 있다.

module_init() : 커널 모듈이 로드될 때 처음 실행할 초기화 함수를 등록하는 메크로
```

드라이버 객체에서는 <code>file_operations</code>를 따라 <code>open</code>, <code>ioctl</code>, <code>read</code> 같은 실제 핸들러를 찾고, 장치 객체에서는 사용자 공간에 보이는 장치 파일 이름을 찾는다.

```c
file_operations() : 파일이나 장치에 어떤 시스템들이 들어왔을 때 커널 함수를 실행할지
연결해주는 구조체이다.
```

즉 단순히 <code>.ioctl</code>이라는 이름이 있다는 이유만으로 핸들러라고 판단하지 않고, <strong>실제 초기화와 등록 관계를 따라가며 진짜 인터페이스를 찾는 것</strong>이 핵심이다.

### 3.2 전체 구조

SyzDescribe는 <strong>Linux 커널 모듈의 LLVM 비트코드</strong>를 입력으로 받아 분석하고, 최종적으로 <strong>syzkaller가 사용할 시스템 콜 설명</strong>을 만든다.

```c
 LLVM : C/C++ 같은 코드를 바로 기계어로 바꾸는 과정 중간에 공통된 형태로 바꿔서 분석하고,
 최적화할 수 있게 해주는 도구 모음

 LLVM 비트코드 : 커널 모듈의 C 소스코드를 LLVM이 분석하기 좋은 중간 표현으로 바꾼 것
```

전체 과정은 크게 두 단계이다.

1. <strong>커널 모듈 분석:</strong> 드라이버가 어디서 초기화되는지 찾고, 장치 파일 이름과 시스템 콜 핸들러를 복구한다.
2. <strong>시스템 콜 핸들러 분석:</strong> 찾은 핸들러 안에서 <code>ioctl</code> 명령 값, 인자 형식, 파일 디스크립터 의존 관계를 복구한다.

> <strong>저 어떤 드라이버와 인터페이스가 존재하는지 찾고, 그 다음 그 인터페이스를 어떻게 호출해야 하는지 세부 정보를 찾는 구조</strong>

### 3.3 커널 모듈 분석

#### 3.3.1 커널 모듈 식별

SyzDescribe는 먼저 <strong>모듈 초기화 함수</strong>를 찾는다. <code>module_init()</code> 같은 초기화 정보를 이용해 분석의 시작점을 정하고, 여러 모듈이 관련되어 있다면 초기화 순서도 함께 확인한다.

#### 3.3.2 커널 드라이버 식별

다음으로 <strong>드라이버 객체와 장치 객체</strong>를 찾는다.<br /><strong>(syzDescribe가 정적 분석으로 찾는다)</strong>

드라이버 객체에서는 시스템 콜 핸들러 정보를 얻고, 장치 객체에서는 장치 파일 이름을 얻는다. 두 객체의 <strong>major/minor 장치 번호</strong>를 비교하여 같은 드라이버 인터페이스에 속하는지 연결한다.

```c
major/minor : 장치 파일과 실제 커널 드라이버를 구분하고 연결하기 위해 쓰는 번호
```

그 후 <code>file_operations</code>에서 <code>open</code>, <code>ioctl</code>, <code>read</code> 같은 실제 핸들러를 찾는다.

### 3.4 시스템 콜 핸들러 분석

#### 3.4.1 명령 값 복구

<code>ioctl()</code>은 하나의 함수 안에서도 <strong>명령 값에 따라 서로 다른 기능</strong>을 수행할 수 있다. SyzDescribe는 <code>switch-case</code>와 <code>if</code> 조건을 분석하여 어떤 명령 값이 존재하는지 찾는다.

#### 3.4.2 인자 형식 복구

<code>ioctl()</code>의 세 번째 인자는 실제로 특정 구조체의 주소로 사용되는 경우가 많다. SyzDescribe는 <code>copy_from_user()</code> 같은 함수의 사용을 보고 <strong>어떤 자료형의 데이터를 전달해야 하는지</strong> 추론한다.

```c
copy_from_user() : 사용자공간에 존재하는 데이터를 커널 공간으로 복사하는 함수이다.
```

#### 3.4.3 추가 시스템 콜 핸들러 복구

일부 <code>ioctl()</code>은 새로운 파일 디스크립터를 만들어 반환한다. 이후 다른 시스템 콜이 이 새 파일 디스크립터를 사용해야 한다면 호출 사이에 <strong>추가 의존 관계</strong>가 생긴다.

SyzDescribe는 이런 관계까지 찾아 시스템 콜 설명에 포함한다.

> SyzDescribe는 먼저 커널 모듈의 초기화 함수에서 분석을 시작해 드라이버 객체와 장치 객체를 찾고, major/minor 장치 번호를 이용해 둘을 연결한다.<br />그다음 <code>file_operations</code>를 통해 실제 <code>open</code>, <code>read</code>, <code>ioctl</code> 등의 시스템 콜 핸들러를 복구한다. 이후 <code>ioctl()</code> 내부의 <code>switch</code>나 <code>if</code>를 분석하여 명령 값을 찾고, <code>copy_from_user()</code> 같은 함수 사용을 통해 각 명령이 요구하는 인자 형식을 추론한다.<br />또한 <code>ioctl()</code>이 새로운 파일 디스크립터를 반환하는 경우 이후 시스템 콜과의 fd 의존 관계까지 복구한다.<br />이렇게 얻은 정보를 최종적으로 syzkaller가 사용할 syscall description으로 변환한다.

## 4. 구현

SyzDescribe는 <strong>LLVM 14 기반의 정적 분석 도구</strong>로 구현되었다.

전체 시스템은 약 <strong>8.2천 줄의 C++ 코드</strong>와 Linux 커널 LLVM 비트코드를 빌드, 연결하기 위한 약 <strong>300줄의 Go 코드</strong>로 구성된다.

커널 모듈 분석에서는 함수 사이의 호출 관계와 자료구조 필드를 추적하고, 시스템 콜 핸들러 분석에서는 명령별 실행 흐름을 구분하기 위해 흐름 민감 분석을 사용한다.

```c
흐름 민감 분석 : 코드가 실행되는 순서와 분기 흐름을 고려해 분석하는 방식
```

### 4.1 커널 모듈 식별

소스 코드 단계에서는 <code>module_init()</code>이나 관련 매크로를 볼 수 있지만, LLVM 중간 표현에서는 전처리가 이미 끝난 상태이므로 원래 매크로가 그대로 남아 있지 않는다.

SyzDescribe는 빌트인 모듈에서 초기화 매크로가 확장된 뒤 남는 어셈블리 패턴을 인식하고, 로드 가능한 모듈에서는 <code>init_module</code>이라는 전역 함수 포인터를 이용해 진입점을 찾는다.

### 4.2 간접 호출 해결

함수 포인터를 통한 <strong>간접 호출</strong>은 커널 정적 분석의 어려운 문제이다. 하나의 호출 지점에서 여러 함수가 후보가 될 수 있기 때문이다.

기존 타입 기반 분석은 가능한 함수 후보를 많이 남길 수 있다.

SyzDescribe는 커널 모듈의 <strong>초기화 순서</strong>를 추가로 활용한다. 특정 간접 호출 시점 이전에 실제로 설정되거나 사용된 함수만 후보로 남기는 방식으로 후보 수를 줄인다.

논문에서는 allyesconfig 환경에서 간접 호출 지점당 평균 후보 수를 <strong>33.2개에서 5.8개로 감소</strong>시켰다고 설명한다.

```c
allyesconfig : Linux 커널 빌드 설정에서 가능한 옵션을 최대한 전부 활성화하는 설정
(분석할 드라이버 수를 최대한 많이 확보하려고 사용함)
```

### 4.3 추가 장치 객체 모델링

기본 장치 객체는 <code>struct device</code>이지만 실제 Linux에는 이를 감싸는 더 높은 수준의 구조체도 존재한다.

```c
struct device : Linux 커널에서 하나의 장치를 표현하는 기본 구조체이다.

예시
struct device {
    // 장치 이름
    // 부모 장치
    // 연결된 드라이버
    // 장치 번호
    // 기타 장치 정보
};
```

SyzDescribe는 대표적으로 다음 네 종류를 추가로 모델링한다.

- <code>struct miscdevice</code> (기타 장치 구조체)
- <code>struct usb_class_driver</code> (USB 클래스 드라이버 구조체)
- <code>struct drm_driver</code> (DRM 드라이버 구조체)
- <code>struct snd_minor</code> (사운드 minor 장치 구조체)

이 구조체들의 등록 API를 모델링하여 내부의 장치 이름, 장치 번호, 시스템 콜 핸들러가 실제 기본 장치 객체와 어떻게 연결되는지 추적한다.

> SyzDescribe는 LLVM 14 기반 정적 분석 도구로 구현되었으며, Linux 커널 비트코드에서 모듈 초기화 지점을 복구하고, 함수 포인터로 인해 발생하는 간접 호출 후보를 초기화 순서를 이용해 줄인다.<br />또한 <code>struct device</code>뿐 아니라 <code>miscdevice</code>, <code>usb_class_driver</code>, <code>drm_driver</code>, <code>snd_minor</code> 같은 특수 장치 구조체도 추가로 모델링하여 장치 이름, 장치 번호, 시스템 콜 핸들러 간의 연결 관계를 더 정확하게 복구한다.

## 5. 평가

저자들은 평가에서 세 가지 연구 질문을 제시한다.

- <strong>RQ1:</strong> SyzDescribe가 생성하는 시스템 콜 설명의 수는 기존 방식과 비교해 어느 정도인가?
- <strong>RQ2:</strong> 생성된 시스템 콜 설명의 정확도와 품질은 어느 정도인가?
- <strong>RQ3:</strong> 생성된 설명이 실제 퍼징에서 얼마나 효과적인가?

주요 Linux 실험은 <strong>Linux 커널 v5.12</strong>를 대상으로 수행되었으며, 설명 생성에는 allyesconfig, 퍼징에는 syzbot 구성을 사용한다.

```c
syzbot : syzkaller를 자동으로 계속 돌려주는 자동화 시스템

syzkaller = 커널을 실제로 퍼징하는 퍼저 도구
syzbot = syzkaller를 이용해서 자동으로 퍼징을 운영하는 역할
```

### 5.1 전체 결과

논문은 시스템 콜 핸들러 구조체 수, 장치 파일 이름 수, <code>ioctl</code> 명령 값과 인자 형식 조합 수, open이 아닌 방식으로 만들어지는 파일 디스크립터 의존 관계 수 등을 비교한다.

| 방법 | 구성 | 핸들러 | 장치 이름 | 명령 값·인자 형식 조합 | 추가 FD 의존 관계 |
| --- | --- | --- | --- | --- | --- |
| <strong>SyzDescribe</strong> | allyes | 415 | 653 | 3,379 | 58 |
| DIFUZE | allyes | 4,334 | 48 | 560 | 0 |
| <strong>SyzDescribe</strong> | syzbot | 185 | 229 | 2,119 | 33 |
| KSG | syzbot | 88 | 1,098\* | 714\* | 0 |
| 수동 syzkaller 설명 | 동일 시점 저장소 | 153 | 232 | 1,737 | 27 |

KSG의 장치 이름 수에는 <code>usbmon0</code>, <code>usbmon1</code>처럼 같은 패턴의 이름이 반복된 경우가 많이 포함되어 있으며, 논문은 이를 묶으면 수가 크게 줄어든다고 설명한다. 명령 값과 인자 형식에도 반복 항목이 존재한다.

DIFUZE가 SyzDescribe보다 훨씬 많은 핸들러를 찾은 것은 더 좋은 결과라는 뜻이 아니다. 이후 정확도 평가에서 이 중 상당수가 실제 핸들러가 아닌 <strong>거짓 양성</strong>임을 확인한다.

### 5.2 SyzDescribe 설명의 정확도

저자들은 무작위로 선택한 <strong>100개의 커널 드라이버</strong>를 사람이 직접 분석하여 정답 데이터인 ground truth를 만들었다.

#### 5.2.1 DIFUZE와 비교

<strong>SyzDescribe는 핸들러와 장치 파일 이름 모두에서 DIFUZE보다 높은 정확도를 보였다.</strong>

특히 핸들러 F1 점수는 SyzDescribe가 <strong>0.95</strong>, DIFUZE 계열은 약 <strong>0.57</strong> 수준으로 보고된다. 장치 이름 역시 SyzDescribe가 더 높은 F1을 보였다.

```c
F1 = 정확도와 재현율을 하나로 합친 지표이다
(찾은 것 중 얼마나 정확했는지, 실제로 있는 것을 얼마나 놓치지 앟았는지 등)
```

DIFUZE는 구조체가 시스템 콜 핸들러 구조체처럼 보이는지를 휴리스틱으로 판단하기 때문에 실제로는 드라이버 내부용인 함수 포인터 구조체까지 잘못 포함할 수 있다.

또한 SyzDescribe는 ground truth에 존재하는 <strong>open이 아닌 파일 디스크립터 의존 관계 6개를 모두 복구</strong>했지만 DIFUZE는 이를 복구하지 못했다.

#### 5.2.2 KSG와 비교

KSG와의 비교에서도 SyzDescribe는 장치 파일 이름을 제외한 대부분의 항목에서 더 높은 결과를 보였다.

핸들러 F1은 SyzDescribe가 <strong>0.99</strong>, KSG가 <strong>0.71</strong>이었다.

KSG는 실제 실행 중인 드라이버만 관찰할 수 있어 일부 드라이버나 인터페이스를 놓치며, 일부 <code>ioctl</code> 명령 값도 정확한 값으로 좁히지 못하는 문제가 있었다.

SyzDescribe는 이 비교에서도 추가 파일 디스크립터 의존 관계 6개를 복구했고 KSG는 복구하지 못했다.

#### 5.2.3 수동 syzkaller 설명과 비교

사람이 관리하는 syzkaller 설명은 이미 알려진 인터페이스에 대해서는 매우 정교할 수 있다. 특히 SyzDescribe가 아직 지원하지 않는 값의 범위 같은 세부 정보도 포함할 수 있다.

하지만 수동 설명은 커널이 변경된 뒤 갱신되지 않거나 일부 명령 값과 인자 형식이 빠질 수 있다.

논문에서는 수동 syzkaller 설명이 이미 존재하는 드라이버를 비교했을 때 SyzDescribe가 <strong>13개 드라이버에서 수동 설명에 없던 78개의 명령 값·인자 형식 조합</strong>을 추가로 찾았다고 설명한다.

즉 두 방식은 완전히 대체 관계라기보다 <strong>서로 보완할 수 있는 관계</strong>에 가깝다.

#### 5.2.4 Ground Truth와의 차이 원인

<strong>SyzDescribe도 완벽하지 않다.</strong>

핸들러 누락은 동적으로 만들어지는 구조체나 특별한 초기화 방식 때문에 발생할 수 있다. 장치 파일 이름은 논문이 모델링한 일반적인 API와 형식 문자열을 사용하지 않고 동적으로 만들어질 경우 놓칠 수 있다.

명령 값은 단순한 동등 비교가 아니라 비트 연산, 매크로 변환, 함수 배열 같은 복잡한 방식으로 처리될 수 있어 정확한 값을 추론하기 어려울 수 있다.

인자 형식은 핸들러나 명령 값을 먼저 놓쳤을 때 함께 누락되거나, <code>copy_from_user()</code> 이외의 사용자 공간 복사 함수가 충분히 모델링되지 않은 경우 놓칠 수 있다.

반면 ground truth에 존재한 <strong>open이 아닌 파일 디스크립터 의존 관계는 모두 정확하게 복구</strong>했다.

### 5.3 퍼징에서의 효과

본 연구에서 SyzDescribe 설명을 실제 syzkaller 퍼징에 사용하여 DIFUZE, KSG, 수동 syzkaller 설명, ground truth와 비교했다.

#### 5.3.1 DIFUZE와 비교

대부분의 드라이버에서 SyzDescribe가 더 높은 또는 비슷한 코드 커버리지를 보였다.

특히 <strong>KVM</strong>에서는 SyzDescribe가 세 개의 추가 파일 디스크립터 의존 관계를 복구했기 때문에 DIFUZE보다 훨씬 더 많은 코드를 도달하고 더 많은 crash를 관찰할 수 있었다.

#### 5.3.2 수동 syzkaller 설명과 비교

수동 설명은 특정 드라이버에서 SyzDescribe보다 좋은 경우도 있었고, 반대로 SyzDescribe가 수동 설명에 없는 인터페이스를 복구해 더 좋은 경우도 있었다.

이는 자동 생성 결과와 사람이 작성한 결과가 서로 다른 정보를 가질 수 있으며, <strong>두 설명을 결합할 가치가 있다는 근거</strong>가 된다.

#### 5.3.3 Ground Truth와 비교

전체적으로 사람이 직접 만든 ground truth가 가장 완전하기 때문에 퍼징 결과도 더 좋은 편이었다.

그러나 SyzDescribe는 자동 생성 방식임에도 ground truth와 크게 멀지 않은 결과를 보였고, 거짓 양성보다 <strong>거짓 음성, 즉 필요한 설명의 누락이 퍼징 성능에 더 치명적</strong>이라는 점도 관찰했다.

#### 5.3.4 KSG와 비교

SyzDescribe는 KSG보다 전반적으로 더 높은 코드 커버리지와 crash 수를 보였다.

KSG는 장치 파일을 실제로 열 수 있고 <code>read()</code>, <code>write()</code> 같은 인터페이스를 다룰 수 있다는 장점이 있지만, 이 부분은 기존 syzkaller 수동 설명에서도 비교적 잘 다뤄지고 있다.

반면 SyzDescribe는 기존 설명에서 부족할 수 있는 드라이버 인터페이스와 의존 관계를 보완하는 데 강점이 있다.

#### 5.3.5 Pixel 6의 Android 커널 드라이버 퍼징

저자들은 실제 Android 환경에서도 SyzDescribe를 적용했다.

Pixel 6 커널에서 <strong>139개 드라이버에 해당하는 154개의 시스템 콜 핸들러</strong>를 복구했고, 생성한 설명으로 <strong>일주일 동안 퍼징하여 18개의 crash</strong>를 관찰했다.

다만 Pixel의 일부 crash는 RAMDUMP MODE와 관련되어 syzkaller가 자동으로 정상 수집하기 어려웠고, 상세한 crash report와 공개 문서가 부족하여 각 crash의 정확한 근본 원인을 모두 분석하지는 못했다.

> 이 결과는 SyzDescribe가 일반 Linux 커널뿐 아니라 실제 Android 커널 드라이버 분석에도 적용될 수 있음을 보여주는 실험이다<br /><br />추가로 저자들은 연구를 진행한 결과를 보고 사람이 만든 syzkaller와 본 연구에서 만든 SyzDescribe를 서로 상호 보완하며 사용하면 좋다와 같은 말을 자주 한다.
>
> 이 결과는 SyzDescribe가 일반 Linux 커널뿐 아니라 실제 Android 커널 드라이버 분석에도 적용될 수 있음을 보여준다. 또한 저자들은 평가 결과를 통해 <strong><u>SyzDescribe와 사람이 작성한 syzkaller 설명이 서로 다른 강점을 가진다</u></strong><strong> </strong>는 점을 반복해서 강조한다.
>
> 사람이 작성한 설명은 세부적인 값이나 범위를 정교하게 표현할 수 있지만, 새로운 인터페이스가 누락되거나 갱신이 늦어질 수 있다. 반대로 SyzDescribe는 사람이 놓친 인터페이스나 명령 값, 인자 형식, 파일 디스크립터 의존 관계를 자동으로 찾아낼 수 있다.
>
> 따라서 두 방식을 경쟁 관계로 보기보다는, <strong>자동 생성 결과와 수동 설명을 함께 사용하여 더 완전한 시스템 콜 설명을 만드는 방향이 효과적이라고 본다.</strong>

## 6. 한계 및 향후 연구

SyzDescribe에는 몇 가지 명확한 한계가 있다.

### 특정 값과 값의 범위

현재 SyzDescribe는 <code>ioctl()</code> 인자의 <strong>자료형</strong>은 복구하지만, 특정 인자가 가져야 하는 정확한 값이나 허용 범위까지 복구하지는 않는다.

### 다른 시스템 콜

SyzDescribe는 시스템 콜 핸들러를 찾을 수 있으므로 원칙적으로 <code>read()</code>, <code>write()</code>, <code>mmap()</code> 같은 다른 인터페이스도 설명할 수 있다.

하지만 각 시스템 콜에서 어떤 인자 형식과 값이 필요한지 자동 추론하는 문제는 아직 해결하지 않았다.

### 다른 명시적 의존 관계

현재 구현은 <strong>파일 디스크립터와 관련된 명시적 의존 관계</strong>에 집중한다. 다른 종류의 시스템 콜 의존 관계는 별도의 분석이 필요하다.

### 시스템 콜 설명 병합

SyzDescribe가 생성한 설명과 사람이 작성한 syzkaller 설명은 서로 다른 정보를 가지고 있어 상호 보완적이다.

저자들은 향후 자동 분석 결과와 사람의 설명을 병합하여 <strong>하나의 더 완전한 시스템 콜 설명을 지속적으로 유지하는 방향</strong>이 유망하다고 본다.

> - <strong>값의 범위까지는 못 찾음</strong>: <code>ioctl()</code>에 어떤 자료형을 넣어야 하는지는 알아내도, 그 값이 <code>1~10</code>이어야 하는지, 특정 상수만 가능한지까지는 알아내지 못했다.
> - <strong><code>read()</code></strong><strong>, </strong><strong><code>write()</code></strong><strong>, </strong><strong><code>mmap()</code></strong><strong> 분석은 아직 부족함</strong>: 핸들러 자체는 찾을 수 있지만, 각 시스템 콜에 어떤 인자와 값이 필요한지까지 자동으로 설명하지는 못한다는 결론을 내렸다.
> - <strong>FD 말고 다른 의존 관계는 잘 못 다룸</strong>: 지금은 주로 앞에서 얻은 fd를 다음 syscall에서 써야 한다” 같은 관계에 집중하고 있는 것이 드러난다.  다른 종류의 syscall 간 의존성은 추가 분석이 필요하다고 느낀다.
> - <strong>사람이 만든 설명을 완전히 대체하지는 못함</strong>: SyzDescribe가 자동으로 찾는 정보와 사람이 작성한 syzkaller 설명이 서로 다르기 때문에, 결국 둘을 합치는 방향이 더 완전하다고 느낀다.

## 7. 관련 연구

MoonShine은 기존 테스트 실행 흔적을 이용해 syzkaller의 seed를 개선하고, SyzVegas와 HEALER 같은 연구는 테스트 생성과 시스템 콜 관계 학습을 개선한다.

HFL은 symbolic execution을 결합해 중첩 인자 형식과 파일 디스크립터 의존 관계 등을 분석한다. 다만 HFL의 주목적은 시스템 콜 설명 자체를 직접 생성하는 것은 아니다.

SyzGen은 폐쇄형 macOS 드라이버의 시스템 콜 설명을 생성하지만, 기존 실행 trace에 장치 파일 이름과 기본 인터페이스 정보가 이미 포함되어 있다는 점에서 SyzDescribe와 출발점이 다르다.

SyzDescribe의 특징은 <strong>Linux 커널 드라이버의 초기화 과정 자체를 정적으로 분석하여 기본 인터페이스부터 복구한다는 점</strong>이다.

## 8. 결론

SyzDescribe는 Linux 커널 드라이버의 시스템 콜 설명을 정적 분석으로 자동 생성하기 위한 방법을 제안한다.

핵심은 <strong>커널 모듈 초기화 과정과 Linux 커널 코어·드라이버 사이의 계약을 이해하고 모델링하는 것</strong>이다. 이를 이용하여 드라이버 객체와 장치 객체를 연결하고, 장치 파일 이름과 시스템 콜 핸들러를 복구하며, <code>ioctl()</code>의 명령 값·인자 형식·추가 파일 디스크립터 의존 관계까지 추출한다.

평가 결과 기존 자동화 방식인 DIFUZE와 KSG보다 전반적으로 높은 정확도와 퍼징 효과를 보였고, 사람이 작성한 syzkaller 설명과도 경쟁력 있으면서 서로 보완적인 정보를 제공했다.

다만 동적으로 만들어지는 자료구조, 복잡한 명령 값 처리, 값의 범위, 다른 시스템 콜과 다양한 의존 관계는 여전히 향후 연구 과제로 남아 있다.

> <strong>프로젝트와 연결해서 볼 부분</strong>
>
> 이 논문에서 특히 참고할 부분은 단순히 “어떤 ioctl이 존재한다”를 찾는 것이 아니라 <strong>장치 파일과 실제 커널 핸들러가 어떤 자료구조와 등록 과정으로 연결되는지 근거를 복구한다는 점</strong>이다.
>
> 현재 진행 중인 Android GKI 기반 분석 프로젝트에서도 인터페이스와 커널 구성요소 사이의 연결 관계를 설명하려면, SyzDescribe의 <strong>초기화 과정 추적, 드라이버·장치 객체 연결, file\_operations 추적 방식</strong>이 구조 분석 측면에서 참고가 될 수 있다.
>
> 이 부분은 SyzDescribe 논문의 직접적인 프로젝트 제안이 아니라, 논문 내용을 현재 프로젝트 관점에서 연결해 본 해석이다.
