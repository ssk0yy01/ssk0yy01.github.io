## 인증과 인가의 차이

<strong>인증</strong> : 사용자가 누구인지 확인하는 과정

<strong>인가</strong> : 사용자가 무엇을 할 수 있는 권한을 가지고 있는지 확인하는 과정

### 인증 / 인가 차이점

| 구분 | 인증 | 인가 |
| --- | --- | --- |
| 질문 | 누구인지 확인 | 권한을 확인 |
| 방법 | 비밀번호, 지문, 인증서 | 역할, 권한, 정책 |
| 결과 | 신원 확인 | 접근 허용/거부 |
| 순서 | 인가 전에 먼저 실행 | 인증이 완전히 끝나면 인가가 진행 |
| 변경 빈도 | 자주 바뀌지 않음 (본인 정보) | 자주 바뀜 (권한 부여/회수) |

### 인증 / 인가 예시

예시 : 온라인 쇼핑몰 주문 취소

인증

- 쇼핑몰 사이트 로그인

- 서버가 데이터베이스를 조회해 입력한 비밀번호와 저장된 값을 비교 → 인증 완료 되고 로그인 성공

인가

- 자신이 주문한 물건을 취소하게 된다.

## 로그인 상태 유지

### 왜 필요한가?

HTTP는 <strong>무상태(stateless) 프로토콜</strong>이다. 즉, 서버는 각 요청을 독립적으로 처리하며, 이전 요청에서 누가 로그인했는지 <strong>기억하지 못한다</strong>.

그래서 사용자가 로그인한 뒤 페이지를 이동하거나 API를 호출할 때마다 매번 로그인을 다시 하지 않으려면, <strong>로그인 상태를 유지하는 별도의 방법</strong>이 필요하다. 대표적으로 두 가지 방식이 있다.

---

### 1) 세션 기반 인증 (Session-based)

<strong>서버가 사용자의 로그인 상태를 기억하는 방식</strong>이다.

### 동작 방식

1. 사용자가 로그인하면 서버는 <strong>세션 저장소</strong>에 사용자 정보를 저장하고 고유한 <code>Session ID</code>를 발급한다.
2. 발급된 Session ID는 클라이언트의 <strong>브라우저 쿠키</strong>에 저장된다.
3. 이후 사용자가 요청을 보낼 때마다 쿠키에 담긴 Session ID가 함께 전송된다.
4. 서버는 세션 저장소에서 해당 ID를 조회해 로그인 상태를 확인하고 응답한다.

### 세션 저장 위치

서버의 <strong>메모리, 디스크, 또는 데이터베이스</strong>에 저장된다.

### 단점

- <strong>서버 재부팅 시 세션 정보가 사라질 수 있음</strong> → 사용자가 다시 로그인해야 함 (메모리 저장 시)
- <strong>서버 확장(Scale-out)이 어려움</strong> → 서버를 여러 대 운영할 경우, 모든 서버가 같은 세션을 공유해야 하므로 별도의 세션 저장소(Redis 등)가 필요해진다.

### 2) 서명된 토큰 기반 인증 (Token-based)

<strong>서버가 아닌 클라이언트가 인증 정보를 보관하는 방식</strong>이다.

### 동작 방식

1. 사용자가 로그인하면 서버는 <strong>사용자 정보 + 서명</strong>이 담긴 <strong>토큰(문자열)</strong>을 발급한다.
2. 클라이언트는 이 토큰을 보관한다 (보통 localStorage 또는 쿠키).
3. 이후 요청을 보낼 때마다 토큰을 함께 전송한다.
4. 서버는 허용한 알고리즘과 키로 <strong>서명</strong>을 검증하고, 만료 시간·발급자·대상 서비스 등 필요한 클레임도 확인한다. 이후 해당 요청에 대한 권한을 별도로 검사한다.

서명된 JWT의 내용은 일반적으로 암호화된 것이 아니므로 비밀번호 같은 비밀 정보를 넣으면 안 된다. 토큰을 폐기하거나 갱신하는 설계에서는 서버에 상태를 보관하기도 한다. [OWASP REST Security](https://cheatsheetseries.owasp.org/cheatsheets/REST_Security_Cheat_Sheet.html#jwt)

### 핵심 특징: 무결성 보장

토큰 안에는 <strong>서버에서 발급되었음을 증명하는 서명</strong>이 들어있다. 따라서 누군가 토큰의 내용을 변조하면 서명이 깨져 즉시 탐지된다. 이를 <strong>무결성(Integrity)</strong> — 정보가 변경·위조되지 않는 성질 — 이라 한다.

### 장점

- <strong>서버 리소스 절약</strong>: 서버가 로그인 정보를 따로 기억하지 않아도 됨
- <strong>확장에 유리</strong>: 서버가 여러 대여도 토큰만 검증하면 되므로 세션 공유가 불필요
- <strong>상태 비저장(Stateless)</strong> 아키텍처와 잘 맞음

---

### 두 방식 비교

| 구분 | 세션 기반 | 서명된 토큰 기반 |
| --- | --- | --- |
| 인증 정보 저장 위치 | <strong>서버</strong> (세션 저장소) | <strong>클라이언트</strong> |
| 서버가 보관하는 것 | 세션 데이터 | 서명 검증 키·설정, 필요에 따라 폐기·갱신 상태 |
| 서버 리소스 사용 | 세션 저장·조회 비용 | 서명·클레임 검증 비용 |
| 서버 확장성 | 세션 공유 필요 (까다로움) | 용이함 |
| 재부팅 시 | 저장소의 영속성에 따라 다름 | 검증 키·설정의 유지 여부에 따라 다름 |
| 대표 예시 | 세션 ID를 사용하는 로그인 | 서명된 JWT를 사용하는 구성 |

## IDOR

### IDOR(Insecure Direct Object Reference)?

- IDOR은 안전하지 않은 직접 객체 참조라는 뜻으로 웹 애플리케이션 보안 취약점의 한 종류이다.
- 사용자가 URL이나 양식 매개변수와 같은 참조를 통해 내부 구현 객체에 직접 접근할 수 있을 때 발생

예시 : <code>GET /api/user/1234/profile</code>

<br />여기서 <code>1234</code>를 <code>1235</code>로 바꿨을 때 다른 사람의 프로필이 그대로 노출된다면 IDOR이다.

(인증은 통과 했지만, 인가 검증이 제대로 이루어지지 않아 발생)

### IDOR의 역할 / 목적

- 권한 우회 : 인증된 사용자가 접근 권한이 없는 리소스에 접근
- 민감한 정보 유출 : 다른 사용자의 개인 정보나 기밀 데이터 열람
- 데이터 조작 : 권한 없는 데이터 수정, 삭제 또는 생성
- 수평적 권한 상승 : 동일한 권한 수준의 다른 사용자 리소스에 접근
- 수직적 권한 상승 : 높은 권한 수준의 리소스에 접근

### 구조 및 작동 원리

기본 메커니즘

1. 객체 참조 노출 : 웹 애플리케이션이 내부 객체를 사용자에게 직접 노출
2. 불충분한 접근 제어 : 해당 객체에 대한 접근 권한 검증이 불충분하게 구현됨
3. 요청 조작 기능 : 사용자가 객체 참조를 쉽게 조작하여 의도하지 않은 접근을 시도할 수 있음

방어방법

- 모든 객체 접근 요청에서 "현재 세션 사용자가 해당 객체의 소유자/권한자인지" 서버 측에서 검증
- 순차적이고 추측 가능한 ID 대신 UUID 등 예측 불가능한 식별자 사용 (보조 수단이며 근본 대책은 아님)
- 권한 검증 로직을 공통 미들웨어/데코레이터로 강제

## 권한 체크 실수

<strong>보안에서의 권한체크 실수</strong>

- 사용자가 어떤 자원이나 기능에 접근할 자격이 있는지를 제대로 검증하지 못해 생기는 결함

<strong>인증 누락/우회</strong>

- 로그인 없이 접근 해버리거나 쿠키/세션 검증을 빠뜨림

<strong>인가 실수 </strong>

- 권한이 없는 사용자에게 권한이 주어지거나 볼 수 없는 페이지를 보게 됨

이 취약점은 OWASP TOP10에도 등록된 아주 강력한 취약점이다.

### 권한 검증이 빠졌을 때의 예시

<strong>예시: 페이지 관리자 추가 요청의 권한 검증 누락</strong>

페이지 관리자를 추가하는 요청에서 서버가 "요청한 사람이 관리자 추가 권한을 갖고 있는지"를 검증하지 않는 상황을 생각해 보자. 이때 페이지 ID와 계정 ID를 바꾼 요청이 그대로 허용되면, 다른 사람의 페이지에 자신을 관리자로 등록할 수 있다. 객체별 권한 검증이 필요한 이유다.

## 관리자 기능 보호

일반 사용자보다 강력한 권한을 가진 기능을 자격있는 사람만, 안전한 방식으로 쓰게 만드는 것

인가, 인증 강화, 관리자 화면 접근 통제, 최소 권한 원칙 등이 존재한다.

### 보호기법(대표적 2가지)

1. 서버 측 인가 검증

   모든 관리자 요청에 대해 "이 요청자가 admin 권한이 있는가"를 서버에서 매번 확인하는 것. UI에서 버튼을 숨기는 건 보호가 아니고, 서버가 직접 들어온 요청을 검사해야 함.

2. 리눅스 권한

   리눅스에서도 <code>su -</code>나 <code>sudo</code>로 root가 될 때, 기본은 비밀번호 하나만 묻는다.

   하지만 root는 시스템 전체를 장악하는 권한이라, 비밀번호가 유출되면 끝임

   그래서 웹의 관리자 MFA처럼 <strong>권한 상승에 두 번째 요소를 추가</strong>할 수 있다.<br /><br />
